# TEST_INSTRUCTIONS.md

请为当前项目建立完整、可维护的自动化测试体系，覆盖前端、后端和跨端三部分。

要求：

1. 先完整阅读项目结构、README、AGENTS.md / CLAUDE.md、配置文件和核心源码，理解技术栈、模块职责和主要业务流程后再开始修改。
2. 分析现有测试体系：
   - 已使用的测试框架、配置和脚本
   - 已有测试及覆盖范围
   - 缺失的重要测试
3. 根据项目实际技术栈选择合适的测试工具，不要无必要引入重复框架。
4. 为以下部分补充测试：
   - 前端：组件、Hooks、状态管理、工具函数、表单、接口调用、异常状态和关键用户交互。
   - 后端：API、Service、Repository、数据库操作、依赖注入、权限/鉴权、异常处理、核心业务逻辑和边界情况。
   - 跨端：主进程/客户端逻辑、IPC/通信、前后端交互、关键跨端流程及异常情况。
5. 测试至少覆盖：
   - 正常流程
   - 边界条件
   - 非法输入
   - 异常处理
   - 关键业务流程
   - 容易发生回归的问题
6. 合理使用 Mock / Fixture / Test Database，避免测试依赖真实外部服务或污染生产数据。
7. 测试应稳定、可重复执行，避免依赖测试执行顺序。
8. 不要为了提高覆盖率编写没有实际价值的测试；优先保证关键业务逻辑和核心用户流程。
9. 补充或完善测试配置，并提供统一的一键测试入口，使我可以通过一个命令执行前端、后端和跨端全部测试。
10. 如果项目适合，增加：
    - 单元测试
    - 集成测试
    - E2E 测试
    - Coverage 覆盖率统计
11. 运行全部测试，修复由测试暴露出的明确问题，但不要为了让测试通过而改变正确的业务行为。
12. 最后输出简洁总结：
    - 新增/修改了哪些测试
    - 测试覆盖哪些核心功能
    - 如何运行单独测试
    - 如何一键运行全部测试
    - 当前仍未覆盖的重要风险点
13. 检查测试是否适合接入 CI，在必要时补充 CI 测试命令或配置，确保后续每次提交/PR 都能自动验证。
14. 检查测试隔离性和测试数据生命周期，确保数据库、临时文件、环境变量、Mock 等在测试结束后正确清理。
15. 对无法稳定自动测试或暂不适合测试的部分，不要强行编写脆弱测试；记录原因、风险和后续建议。

目标：建立真正能够发现 Bug、防止回归、支持后续持续开发的测试体系，而不是单纯追求测试数量或覆盖率数字。
